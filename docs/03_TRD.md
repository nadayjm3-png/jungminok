## 1. 구현 방향과 전제

브라우저에서 화면·계산·파일 처리를 실행하고 기록은 그 브라우저의 내부 저장소에 보관한다. GitHub는 프로그램 코드 보관소, Vercel은 프로그램 파일을 제공하는 배포 서비스로 사용한다. 실제 판매·비용·재고를 GitHub나 Vercel에 저장하는 구조가 아니다.

사용자는 같은 기기·같은 브라우저·같은 운영 주소에서 다시 열면 저장 기록을 이어서 사용한다. 기기/브라우저/사이트 주소를 바꾸면 저장소가 달라지므로 전체 백업 파일을 복원해 이동한다. 자동 기기 동기화는 PRD에 없으므로 포함하지 않는다. FRD F-10의 저장 유지 범위는 미정이므로 이 경계는 **기술 제안의 전제**이며, 여러 기기에서 자동으로 같은 자료를 사용해야 한다면 개발 전 저장 설계를 다시 검토해야 한다.

별도 서버 데이터베이스와 로그인은 1차에 추가하지 않는다. 기존 기능은 유지하고 구현 부담·서버 비용을 줄이기 위한 설계다. 로컬 저장은 별도 백업 없이 영구 보존을 보장하지 않는다. 브라우저 자료 삭제·저장 공간 정리·기기 고장에 대비하는 수단은 PRD의 전체 백업/복원이다.

## 2. 요구사항의 확정 상태를 보존하는 규칙

이번 요청은 구현 방법을 정하는 요청이며 FRD의 미정 계산·입력 정책을 승인하는 요청으로 해석하지 않는다.

| 구분 | TRD 처리 |
|---|---|
| PRD 필수 기능 F-00~F-10 | 아래 기술 구조와 모두 연결한다. 시안이 없어도 누락하지 않는다. |
| FRD C-01~C-08 계산 제안 | 계산 모듈과 검사 위치를 지정하되 공식·평균 기간·반올림 정책을 바꾸거나 확정하지 않는다. |
| FRD D-01~D-11 미정 동작 | 승인 전 실행 가능한 기본값을 임의로 넣지 않는다. 해당 정책을 결정한 뒤 FRD와 검사표에 반영한다. |
| FRD X-01~X-17 시안 충돌 | 시안 숫자/문구/임시 코드를 구현 기준으로 채택하지 않는다. PRD 사용 범위를 따른다. |
| 기술 결정 | 라이브러리, 저장 구조, 코드 분리, 배포·오류 처리 기술은 이 TRD에서 선택한다. |

FRD는 현재 검토용 초안이며 첫 질문 D-01도 미응답 상태다. 사용자 최신 요청의 '사용 범위는 PRD를 따른다'에 따라 기술 설계의 구현 대상은 PRD 필수 범위로 제한한다. PRD·FRD 파일 자체와 결정 표시는 변경하지 않는다.

전체 기능 출시에는 신규 판매 원가/수수료, 마감 갱신, 파일 중복 처리, 실사 순서, 비용 전망 등 FRD의 핵심 미정 사항 확정이 필요하다. 설계·기반 구현은 진행할 수 있지만, 미정 계산을 임의로 작동시킨 결과를 최종 제품으로 배포하지 않는다.

| decimal.js | 소수 원가를 계산할 때 오차를 줄이는 도구 | 금액·원가·비율 계산. 사업상의 반올림 기준은 FRD 승인값 적용 |
| Web Worker | 화면을 멈추지 않고 뒤에서 일하는 브라우저 기능 | 엑셀 읽기·큰 계산을 화면과 분리 |
| Vitest / Testing Library | 계산과 화면 동작을 자동 검사하는 도구 | FRD 계산·입력·저장 흐름 검증 |

| GitHub / Vercel | 코드 보관소 / 배포 서비스 | 변경 이력 보관과 빌드·미리보기·운영 배포 |

Vite는 React/TypeScript 프로젝트와 정적 배포를 지원하며 Vercel에서 Vite 프로젝트를 배포할 수 있다. [Vite 시작](https://vite.dev/guide/), [Vite 배포](https://vite.dev/guide/static-deploy.html)

IndexedDB는 브라우저의 구조화된 데이터 저장 기능이다. Dexie의 거래 처리(transaction)는 관련 저장을 한 묶음으로 완료하거나 취소하게 한다. 이 기능으로 복원 도중 일부만 바뀌는 문제를 막는다. [IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API), [Dexie 거래 처리](https://dexie.org/docs/Dexie/Dexie.transaction%28%29)

ExcelJS의 브라우저용 .xlsx 읽기/쓰기 지원은 구현 시 브라우저 시험으로 확인한다. Node 전용 파일 경로 API와 서버용 스트리밍 기능은 쓰지 않는다. [ExcelJS](https://github.com/exceljs/exceljs)

개발·Vercel 빌드 환경은 Node.js 24 LTS 계열로 맞춘다. 구체적인 패치 버전과 라이브러리 버전은 구현 시작 시 호환성 검사 후 `package-lock.json`과 런타임 설정에 고정한다. 이 문서는 '최신'이라는 이동하는 버전을 설치 기준으로 쓰지 않는다. [Node.js 릴리스](https://nodejs.org/en/about/previous-releases)

## 4. 전체 구조

```text
GitHub: 코드 + 요구사항 + 가상 샘플 + 검사 코드
                   │ Vercel에서 빌드
                   ▼
Vercel: HTML / CSS / JavaScript / 공개 가능한 가상 샘플
                   │ HTTPS로 프로그램 제공
                   ▼
사용자 브라우저
  화면 → 입력 검사 → 기능 처리 → 계산 → IndexedDB 저장
       ← 저장 완료와 동일 자료 버전의 결과 표시
  판매 엑셀 선택 → 로컬 검사 → 확인 → 판매 저장
  전체 백업 → 사용자 컴퓨터 파일
  전체 복원 ← 사용자 컴퓨터 파일
```

웹 API, Vercel Functions, 서버 파일 저장, 외부 DB 요청은 1차 구조에 없다. 계산과 파일 처리는 브라우저에서 끝난다. 서버를 추가해야만 가능한 공동 사용·로그인·POS 연동은 범위를 확장할 때 다시 설계한다.

코드를 네 부분으로 나눈다.

1. **화면:** 시안의 표·버튼·입력·팝업과 결과 표시.
2. **기능 처리:** 판매/비용 변경·가져오기·백업·복원의 실행 순서.
3. **계산:** 입력 자료와 승인된 정책을 받아 결과만 만드는 함수. 화면이나 저장소를 직접 수정하지 않는다.
4. **저장/파일:** IndexedDB와 엑셀·JSON 읽기/쓰기. 계산 기준을 가지지 않는다.

같은 계산 함수를 미리보기·저장 후 결과·목록·요약·검사에서 재사용한다. 화면마다 원가/수수료를 따로 계산하지 않는다.

비용·백업·기본 조회 화면의 상세 시안은 없으므로 기존 공통 색·표·입력 부품을 사용하되 FRD 필드/버튼 확인 상태를 유지한다. 추가 메뉴와 운영 기능을 기술 편의를 위해 만들지 않는다.

앱 내부 화면 이동은 해시 주소 방식(예: `/#/sales`)으로 처리한다. Vercel에 서버 라우팅을 추가하지 않고 새로고침 시 같은 프로그램을 연다. 이 주소는 기술 예시이며 화면 이름/동작은 FRD를 따른다.

시안의 정적 HTML을 React 부품으로 옮기고 샘플 고정 숫자를 제거한다. 실제 메뉴ID·재료ID·공급사와 저장 자료를 사용한다. 시안 `_3`의 `alert` 저장, 모든 메뉴에 같은 원두/우유를 넣는 임시 계산, 3.0%/3.3% 수수료, 고정 마감 날짜를 재사용하지 않는다.

실제/예상은 텍스트로 구분하고 단위를 함께 표시한다. 숫자는 오른쪽 정렬과 일정 폭 숫자를 사용한다. 키보드로 입력/확인/취소 가능하게 하며 팝업 열기·닫기의 초점을 관리한다. 반응형 배치는 시안 가이드를 따르며 모바일 전용 앱을 만들지 않는다.

## 6. 데이터 저장 설계

### 6.1 저장할 원본 자료

DB 이름은 `prep-cafe-ledger`, 초기 구조 버전은 1로 계획한다. 구조 버전은 저장 형식의 버전이고, 샘플 JSON의 `meta.version`은 데이터셋 버전이다. 서로 대체하지 않는다.

| 저장 표 | 기록과 주요 연결 | 조회용 색인 |
|---|---|---|
| suppliers | 공급사ID, 이름, 출처 구분 | ID |
| materials | 재료ID, 단위, 구매용량, 가격, 납기/안전재고, 공급사ID | ID, 공급사ID |
| menus | 메뉴ID, 이름, 기준가, 분류, 레시피 버전 | ID, 분류 |
| recipes | 레시피 버전·메뉴ID·재료ID·채널 조건·사용량 | 메뉴ID+버전, 재료ID |
| price_history | 재료ID·적용시작일·구매가격·용량 | 재료ID+적용시작일 |
| calendar | 일자, 영업여부, 마감여부, 원본 메모/날씨 | 일자 |
| sales | 판매ID, 일자, 메뉴ID, 채널, 수량, 당시 금액/원가, 레시피 버전 | 일자, 메뉴ID, 일자+메뉴ID+채널 |
| opening_inventory | 재료ID·기준일·수량·단위 | 재료ID+기준일 |
| inventory_events | 기록ID·일자·재료ID·유형·증감·실측량·선택 비용/공급사 | 일자, 재료ID+일자 |
| expenses | 비용ID·귀속일·항목·금액·원본 배분기준 | 귀속일, 귀속일+항목 |
| monthly_expense_plan | 귀속월·항목·월금액 | 귀속월+항목 |
| app_meta | 원본 meta, settings, 초기화 완료, 형식 버전, dataRevision | 고정 키 |

색인은 원하는 기록을 빠르게 찾는 기준이다. 동일한 날짜·메뉴·채널을 DB의 고유 제약으로 금지할지는 FRD 중복 정책 승인 전 정하지 않는다. 실제 기록 ID는 고유하다. 원본 ID는 유지하고 새 기록은 UUID로 생성해 원본 ID와 충돌하지 않게 한다.

레시피는 한 메뉴에 여러 행이 있으므로 메뉴ID 하나를 행 식별자로 사용하지 않는다. 복합 식별자는 자료 검증을 통과한 버전·메뉴·재료·채널 조합으로 만든다. 충돌하면 임의로 마지막 행만 남기지 않는다.

### 6.2 자료 표현과 계산 결과

- 일자는 `YYYY-MM-DD` 문자열, 귀속월은 `YYYY-MM`로 관리한다. 날짜를 UTC 시각으로 바꿔 하루 앞뒤로 밀리지 않게 한다.
- 백업 생성시각 등 실제 시각은 ISO 8601 UTC로 저장하고 한국 시각으로 표시한다. 자료 기준일과 생성시각은 구분한다.
- 입력 빈 문자열·누락·null·숫자 0을 분리한다. 원본 필드 유무와 '해당 없음' 의미를 변환 검사에서 보존한다.
- 금액·소수 수량은 자료 경계에서 검사하고, 소수 계산에는 decimal.js를 사용한다. 정확한 내부 값은 필요 시 십진 문자열로 보존한다. 저장 형식 변환은 금액 의미를 바꾸지 않는다.
- 원본 판매 당시 순매출·수수료·개당 원가는 유지한다. 신규 저장 시 원가 확정/수정 방식은 FRD D-03을 따른다.
- 기초자료와 거래 기록을 저장의 기준으로 삼는다. 메뉴 합계·손익·재고 잔량·발주량은 다시 만들 수 있는 계산 결과이며 별도 영구 원장으로 이중 저장하지 않는다.
- 결과 캐시는 메모리에 두고 `dataRevision + 승인 정책 버전 + 조회 조건`이 같을 때만 재사용한다. 원가 스냅샷은 당시 기록이므로 이 캐시와 다르다.

### 6.3 안전한 저장과 변경

판매 저장·수정·삭제, 비용 변경, 재고 입력, 파일 일괄 등록, 복원은 다음 기술 순서를 사용한다. 사용자에게 보이는 실행 순서는 FRD를 따른다.

1. 현재 자료와 증가 번호 `dataRevision`을 읽는다.
2. 사용자 입력을 검사하고 변경 후보 자료를 메모리에 만든다. 승인된 규칙으로 연결 결과를 계산한다.
3. Dexie의 한 쓰기 거래 안에서 현재 revision을 다시 검사한다. 자료가 바뀌었으면 덮어쓰지 않고 다시 검사하도록 알린다.
4. 변경할 원본 기록과 증가한 revision을 같은 거래에서 저장한다. 거래가 실패하면 전부 취소된다.
5. 거래 완료 후 그 revision의 화면 결과를 반영한다. 성공 저장 뒤 계산/표시가 실패하면 '저장은 완료, 결과 표시 실패'로 구분하고 재조회한다.

기록 저장 후 재고 사건을 별도로 추가하며 두 번 차감하지 않는다. 재고 사용은 승인된 계산에서 원본 판매로부터 산출한다. 삭제/과거 수정도 같은 재산출 경로를 사용한다.

Dexie 거래 안에서는 엑셀 읽기·파일 해시·Worker 계산·외부 요청을 기다리지 않는다. 이런 작업은 거래 전에 완료하고, 실제 거래에는 DB 읽기/쓰기만 넣는다. 거래 자동 종료와 충돌을 피한다. [Dexie 거래 동작](https://dexie.org/docs/Dexie/Dexie.transaction%28%29)

한 탭에서는 변경 작업을 직렬 실행한다. 여러 탭에서도 DB 거래 안의 revision 비교로 오래된 입력/검사 결과가 현재 자료를 덮어쓰지 않게 한다. 탭 갱신 신호는 화면 최신화를 위한 내부 처리이며 공동 편집 기능을 추가하는 것이 아니다.

### 6.4 초기화·저장소 한계

가상 샘플 JSON을 최초 한 번 검사해 저장하고 초기화 완료 표시도 같은 거래에 넣는다. 프로그램 업데이트·재접속·복원 후 샘플을 다시 합치지 않는다. 로딩 오류를 '처음 사용'으로 보고 샘플로 덮어쓰지 않는다.

IndexedDB는 사이트 주소와 브라우저 프로필에 귀속된다. 시크릿 모드, 브라우저 자료 삭제, 저장소 정리 등으로 사라질 수 있다. 브라우저가 허용하면 `navigator.storage.persist()`로 보존을 요청할 수 있으나 허용/영구 보존은 보장하지 않는다. 저장 한도 초과는 오류로 처리한다. [브라우저 저장 한도와 정리](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

전체 저장소가 지워지면 '첫 방문'과 '삭제 후 방문'을 로컬 자료만으로 확실히 구분할 수 없다. 이 경우 복원 필요성을 안내하고 샘플을 실제 매장 복구 자료로 표현하지 않는다. 별도 자동 원격 복구 기능은 추가하지 않는다.

## 7. 계산 구현과 변경 방지

| FRD 계산 | 코드 모듈 | 지킬 기준 |
|---|---|---|
| C-01 판매금액 | salesCalculation | 당시 금액과 신규 입력 정책 보존 |
| C-02 원가/수익성 | recipeCost, menuProfitability | 레시피 버전·채널·날짜 가격, 과거 스냅샷 보존 |
| C-03 기간 손익 | periodProfitLoss | 공통비/직접비 역할 유지, 계획·실적 이중 합산 금지 |
| C-04 기간 경계 | periodRange, calendarSelection | 날짜 경계·미마감·휴무/0 구분 |
| C-05 월말 전망 | monthForecast | 표본·남은 영업일·비용 계획 적용은 승인 정책 사용 |
| C-06 재료/실사 | inventoryReplay | 같은 실사 실측량/조정량 이중 적용 금지 |
| C-07 발주 | reorderAdvice | 평균·납기·안전재고·올림 정책 보존 |
| C-08 숫자 표시 | numberFormat | 표시 반올림과 계산 정밀도 분리 |

TRD는 새로운 공식을 제안하지 않는다. 각 모듈은 FRD의 승인된 공식과 순서만 구현한다. 사업 정책은 버전이 붙은 설정으로 전달하되 설정 화면을 새로 만들지 않는다. 미승인 정책은 숫자 기본값 없이 '정책 확인 대기'로 식별한다. 시안 예시와 FRD 제안을 실사용 설정으로 자동 저장하지 않는다.

계산 반환값은 '정상 값', '자료 부족', '해당 없음', '정책 미확정'을 구분하며 숫자 0과 다르게 표현한다. 실패 이유와 대상 메뉴/재료를 함께 전달한다. 승인 전 계산 골격은 시험 가능하지만 해당 기능의 출시 완료로 보지 않는다.

초기 자료 규모에서는 날짜순으로 정렬한 거래를 한 번 재생해 잔량을 계산하는 구조를 쓴다. 동일 날짜의 순서는 FRD D-07 승인 규칙으로 결정하며 ID나 입력 순서로 사업상의 순서를 임의 확정하지 않는다. 계산 속도를 이유로 실사·과거 수정 의미를 바꾸지 않는다.

## 8. 판매 엑셀 가져오기와 양식

### 8.1 파일 처리 흐름

FRD의 파일 선택→검사→확정 실행 순서를 유지한다.

1. 브라우저 File API로 사용자가 선택한 파일만 읽는다. 앱 서버로 업로드하지 않는다.
2. ExcelJS를 필요한 순간 불러와 Worker에서 .xlsx를 읽고 행/셀 정보를 추출한다.
3. 승인된 양식의 헤더·시트·열을 검사한 뒤 Zod와 같은 입력 검사로 정상 자료 형태로 변환한다.
4. 파일 내·기존 자료 중복 검사 결과를 원래 엑셀 행 번호와 연결한다. 이 단계는 자료를 저장하지 않는다.
5. 확정 시 검사 당시 revision과 현재 revision을 비교하고 승인된 오류/중복 처리 정책을 적용한다.
6. 일괄 변경과 revision을 한 거래에서 저장한 뒤 연결 결과를 갱신한다.

ExcelJS 읽기용 후보 형식은 .xlsx지만 .csv 지원과 파일 제한은 FRD에서 미정이다. 라이브러리 지원 여부를 이유로 .csv나 자유 형식 파일을 새로 허용하지 않는다. 부분 등록·건너뛰기·덮어쓰기는 라이브러리 옵션으로 정하지 않고 승인된 FRD 규칙으로 실행한다.

### 8.2 검증과 파일 안전

- 확장자만 보지 않고 실제 파일 읽기와 구조 검사 결과를 사용한다. 손상·암호·잘못된 형식은 사용자에게 알린다.
- 날짜는 엑셀 날짜 체계와 셀 형태를 확인해 일자로 변환한다. 애매한 문자 날짜는 승인된 해석 규칙이 없으면 보류한다.
- 숫자·문자·빈칸·0을 구분하고 ID를 숫자로 바꾸지 않는다. 지수 표기/자동 날짜 변환으로 잘못된 ID를 만들지 않는다.
- 수식은 실행하지 않는다. 저장된 계산 결과만 읽어 허용할지/수식 셀을 보류할지는 FRD 파일 정책에서 결정한다.
- 숨은 행/시트, 합계 행, 중복 헤더, 불필요한 열의 처리도 승인된 양식 규칙으로 검사한다.
- 외부 링크를 접속하거나 파일 내용을 HTML로 실행하지 않는다. 파일명과 오류 내용은 텍스트로 표시한다.
- 파일 크기, 실제 셀/행 수, 처리 시간에 내부 안전 제한을 두도록 설계한다. 정확한 제한은 부하 검사 후 FRD에 합의해 표시하며 시안의 20MB/10,000행을 승인 없이 채택하지 않는다.
- 취소/파일 교체는 Worker 작업 ID를 무효화한다. 늦게 도착한 이전 파일의 검증 결과를 새 파일 결과로 표시하지 않는다.

### 8.3 양식 생성

승인된 FRD 열 구성 하나로 양식 생성과 가져오기 헤더 검사를 함께 만든다. 양식에는 날짜 형식·원 단위·실제 메뉴ID·허용 채널 안내를 포함한다. 계산된 순매출/원가를 입력할지 보여주기만 할지도 FRD 결정을 따른다.

ExcelJS `writeBuffer()`로 파일을 메모리에서 만들고 Blob 다운로드로 제공한다. 외부 파일 생성 서버를 사용하지 않는다. 파일명·템플릿 버전은 승인된 FRD 규격을 따른다. 오류 행 다운로드와 비용/재고 양식은 추가하지 않는다.

## 9. 전체 백업과 복원

### 9.1 백업 기술 형식

FRD가 제안한 JSON 백업을 기술안으로 설계한다. 최종 사용자 파일 규격 승인은 FRD D-10을 따른다.

파일에는 `formatId`, `schemaVersion`, `appVersion`, `policyVersion`, `exportedAt`, `dataRevision`, 원본 `meta`, 모든 자료 목록과 `settings`를 포함한다. 자료 형식 버전·프로그램 버전·계산 정책 버전을 분리해 해석한다. 계산 캐시는 백업의 필수 자료에 넣지 않고 복원 후 다시 만든다.

내보내기 직전에 미완료 쓰기를 기다리고 같은 읽기 거래에서 모든 표의 일관된 자료를 얻는다. 거래가 끝난 뒤 JSON 직렬화와 다운로드를 실행한다. 백업 파일은 사용자가 저장하며, 파일 생성 성공을 운영체제의 최종 디스크 저장 보증으로 표시하지 않는다.

### 9.2 복원 처리

FRD의 파일 선택→검사→교체 안내→확인→전체 교체→결과 재계산 순서를 유지한다.

- 선택 파일은 메모리에서 파싱하고 전체 목록·필수 필드·ID 유일성·참조 연결·단위·날짜·지원 버전을 검사한다.
- 정상적으로 비어 있는 목록과 목록 자체 누락을 구분한다. 샘플과 복원용 파일을 자동으로 같은 규격으로 간주하지 않는다.
- 승인된 이전 형식 변환이 있으면 메모리에서 수행한다. 새로운/모르는 버전은 기존 자료를 유지하고 복원을 보류한다.
- 확인 전에는 현재 DB를 지우지 않는다. 확인 후 모든 자료 표를 지우고 백업 자료를 넣는 일을 한 거래에서 수행한다.
- 실패하면 전체 거래를 취소한다. 대량 쓰기를 거래 없이 조각별로 확정해 부분 복원 상태를 만들지 않는다.
- 성공 후 로컬 revision을 새 번호로 바꾸고 모든 캐시를 폐기한다. 백업의 과거 revision을 현재 revision으로 그대로 사용하지 않아 이전 Worker 결과와 혼동하지 않게 한다.
- 계산 정책/프로그램의 호환이 안 맞으면 의미가 바뀐 계산으로 조용히 다시 산출하지 않는다. 호환 검사 결과와 사용 가능한 복원 방법을 알린다.

백업과 복원은 사용자 자료 전체를 보존/교체한다. DB 형식 업그레이드나 배포를 이유로 과거 판매의 원가·마감 상태를 다시 쓰지 않는다.

## 10. 개인정보·매장 자료 보호

### 10.1 자료가 이동하는 위치

| 자료 | GitHub / Vercel | 사용자 기기 |
|---|---|---|
| 프로그램 코드·요구사항 | GitHub 저장, 빌드 결과 Vercel 제공 | 브라우저가 프로그램을 받음 |
| 공개 가능한 가상 샘플 | 명시적으로 가상 자료만 배포 가능 | 최초 로딩 후 로컬 사용 |
| 실제 판매·비용·재고·파일 | 앱이 전송하지 않음 | IndexedDB, 선택 파일, 다운로드 백업 |
| 백업 파일 | 저장소/배포 산출물에 포함하지 않음 | 사용자가 관리 |
| 웹 접속 정보 | 호스팅 서비스의 접속 로그가 생길 수 있음 | 업무 기록과는 구분 |

고객 이름·전화번호·카드번호를 수집하는 입력 기능은 만들지 않는다. 원본 ID는 업무 기록 연결을 위한 것이며 고객 ID로 해석하지 않는다. 실제 자료의 메모/파일명에 개인정보가 들어갈 수 있으므로 로그에 원문 행과 파일 내용을 출력하지 않는다.

### 10.2 웹·계정 보안

- GitHub 저장소는 비공개를 기본 기술안으로 사용한다. 그러나 비공개 저장소에서 배포해도 Vercel 웹 주소가 자동으로 비공개가 되는 것은 아니다.
- Vercel로 제공되는 코드와 가상 샘플은 접속자가 볼 수 있다고 전제한다. 실제 매장 데이터는 `public/`, 소스 import, 빌드 결과, Git 기록에 넣지 않는다.
- 가상 샘플만 명시적으로 허용하고 `data/` 전체를 일괄 공개하지 않는다. 실데이터·업로드·백업·`.env.local`은 `.gitignore`로 제외하고 커밋 전 검사한다.
- Vite의 `VITE_` 환경값은 브라우저 코드에 노출된다. 토큰·비밀번호·비공개 API 키를 넣지 않는다. 1차 앱에 서버 비밀키 자체가 필요 없도록 설계한다. [Vite 환경값](https://vite.dev/guide/env-and-mode)
- 파일·메모·이름은 텍스트로 렌더링하고 HTML 삽입/eval을 사용하지 않는다.
- 시안의 Tailwind CDN, 원격 프로필 이미지, 원격 폰트 의존을 제거하거나 자체 제공 자산으로 바꾼다. 아이콘은 패키지 SVG, 글꼴은 라이선스를 확인한 자체 제공/시스템 폰트를 사용한다.
- 운영 빌드에는 외부 분석·광고·세션 녹화 도구를 붙이지 않는다. 업무 자료를 외부 오류 보고 서비스로 전송하지 않는다.
- HTTPS 배포, 동일 출처 자산, 인라인 실행 금지, 외부 프레임 삽입 금지 등 보안 헤더를 Vercel 설정에 적용하고 실제 로딩을 검사한다.

### 10.3 로컬 보호의 한계

IndexedDB와 JSON 백업은 앱 자체에서 암호화한 금고가 아니다. 같은 OS/브라우저 프로필을 사용하는 사람은 자료에 접근할 수 있으며 다운로드 파일도 읽을 수 있다. 단일 사용자 범위에서 OS 로그인·기기 잠금·디스크 암호화와 백업 파일 보관을 운영 전제로 둔다.

앱 내 로그인·비밀번호 백업·암호화 키 관리는 PRD 기능에 없어 추가하지 않는다. 공용 PC 사용이나 여러 직원별 자료 접근 제어가 필수라면 저장/접근 설계와 PRD 범위를 재검토해야 한다. URL을 아는 다른 기기의 방문자는 운영자 IndexedDB를 볼 수 없지만, 운영자 기기의 같은 브라우저에서는 로그인 장벽이 없다는 차이를 안내한다.

## 11. 처리 속도와 용량

제공 자료는 판매 6,112행·비용 3,560행·재고 사건 1,515행이며 JSON은 약 3.46MB다. 이 규모를 1차 검사 기준으로 사용한다. 실제 성능은 아직 측정하지 않았고 아래는 목표다.

| 동작 | 목표 | 확인 환경 |
|---|---|---|
| 저장된 자료 열기와 첫 결과 | 3초 이내 | 일반 Windows PC, 최신 안정 Chrome/Edge, 정상 저장소 |
| 기간/메뉴 조회 변경 | 0.5초 이내 | 제공 샘플, 자료 로딩 후 |
| 단건 저장과 연결 결과 갱신 | 1초 이내 | 샘플에서 판매/비용/재고 변경 |
| 약 10,000행 판매 파일 검사 | 5초 이내 | 정상 양식 시험 파일, Worker 사용 |
| 전체 백업/복원 | 5초 이내 | 제공 샘플 규모, 로컬 파일 처리 |

10,000행은 성능 시험용 규모이며 허용 행 수 규칙을 확정하는 것이 아니다. 최초 인터넷 다운로드 시간은 기기·망에 따라 달라져 목표와 별도로 측정한다.

속도 개선은 계산 기준을 바꾸지 않고 진행한다. 날짜/ID 색인, 메뉴·레시피·가격 조회 Map, 자료 revision별 메모리 캐시를 사용한다. 엑셀 모듈은 처음부터 받지 않고 필요 시 로딩한다. 목록은 승인된 페이지 수만 화면에 렌더링하며 전체 결과 합계를 페이지 수로 제한하지 않는다.

계산/파일 결과에는 작업 ID와 revision을 붙여 과거 작업 결과가 새 화면을 덮지 않게 한다. 처리 중 진행 상태를 표시하고 클릭 응답을 유지한다. 과도한 파일 크기/읽기 시간은 현재 자료를 바꾸기 전에 중단한다. 정확한 제한과 취소 UI는 FRD 미정 상태를 유지한다.

## 13. GitHub 보관과 Vercel 배포

### 13.1 프로젝트 구성

```text
docs/                   PRD 참조 경로, FRD, TRD, 검사 기준
design/                 기존 시안, 구현 참고
src/
  app/                  공통 화면 상태와 이동
  features/             판매·비용·재고·손익·백업 화면
  domain/               승인 계산·날짜·검사 규칙
  storage/              DB 구조·거래·버전 변환
  files/                엑셀·백업 변환
  workers/              무거운 파일/계산 처리
  components/           공통 입력·표·팝업·상태 표시
  assets/               자체 제공 글꼴·아이콘
sample/                 공개 가능한 가상 샘플만
tests/                  계산·저장·브라우저 검사
package.json            실행 명령·호환 런타임
package-lock.json       정확한 설치 버전
vercel.json             배포/보안 헤더 설정
```

현재 `doc/01_prd.md`를 강제로 옮기지 않고 문서 참조 경로를 그대로 유지한다. 이후 파일명/폴더 정리를 하더라도 내용과 승인 상태를 바꾸지 않는다.

### 13.2 빌드와 배포 절차

1. 비공개 GitHub 저장소에 코드와 공개 가능한 샘플·문서·검사를 커밋한다. 실제 파일/백업과 비밀정보가 없는지 확인한다.
2. 로컬에서 `npm ci`로 고정 버전을 설치하고 타입 검사·자동 검사·프로덕션 빌드를 실행한다.
3. Vercel에서 해당 저장소를 연결하고 Framework는 Vite, 출력 폴더는 `dist`로 설정한다. Node 빌드 계열을 로컬과 맞춘다.
4. 배포 빌드 명령은 타입 검사·핵심 검사 후 `vite build`를 실행하도록 구성한다. GitHub 검사만 통과를 기대하고 실패 코드가 자동 배포되는 구조를 피한다.
5. 미리보기 주소에서 FRD 핵심 흐름과 파일·저장·복원·화면 배치를 검증한다. 업무 자료는 미리보기에서 사용하지 않는다.
6. 필수 정책/검사 통과 후 운영 브랜치(`main` 제안)를 운영 배포한다. 이번 작업에서는 저장소 생성·코드 작성·배포를 실행하지 않는다.

GitHub 연결 시 Vercel은 브랜치 변경에 미리보기 배포를 만들고 운영 브랜치 변경에 운영 배포를 만든다. 실제 연결 권한과 계정 플랜은 구현 단계에서 확인한다. [Vercel GitHub 연결](https://vercel.com/docs/git/vercel-for-github)

### 13.3 운영 주소·업데이트·되돌리기

- 운영 주소를 하나로 고정한다. 미리보기·localhost·운영·다른 도메인의 IndexedDB는 각각 따로다.
- 코드 배포는 매장 자료 배포가 아니며 기존 저장소를 초기화하지 않는다. 코드 업데이트 전 필요한 형식 변환과 백업을 검토한다.
- 스키마 변경은 버전 업그레이드 거래로 수행하고 실패하면 기존 자료 유지. 미지원 구조를 만나면 '새 버전으로 열기 필요'를 알리며 샘플로 대체하지 않는다.
- 운영 코드 문제가 있으면 마지막 정상 배포로 되돌릴 수 있도록 Git 커밋/빌드 번호를 기록한다. 그러나 브라우저 DB 구조가 새 버전으로 바뀌었다면 오래된 앱이 읽을 수 있는지 먼저 확인한다. Vercel 롤백이 DB 롤백까지 해주지는 않는다.
- 1차에서는 서비스워커/PWA 오프라인 설치를 추가하지 않는다. 이미 열린 화면에서 로컬 처리는 가능하지만 인터넷 없이 새로 열리는 앱을 보장하지 않는다.

## 14. 오류 대응

| 오류 | 대응 기술과 사용자 결과 |
|---|---|
| 입력/파일 구조 오류 | 공통 검사 결과에 필드·행 번호·읽기 쉬운 이유 포함. FRD 승인 정책에 따라 보류 |
| 중복/오래된 검사 결과 | ID/업무키 검사와 revision 확인. 자동 덮어쓰기/합산 정책을 기술이 결정하지 않음 |
| 저장 한도/DB 차단 | 거래 실패 처리, 성공 표시 금지, 기존 자료 보존. 메모리만 저장하고 영구 저장 성공이라고 안내하지 않음 |
| 다른 탭이 DB 업그레이드 중 | 기존 연결 닫기와 다시 열기 안내. 데이터 삭제로 해결하지 않음 |
| Worker 실패/시간 초과 | 작업 무효화, 파일 재검사 안내. 파싱한 일부 행을 몰래 등록하지 않음 |
| 계산 실패/입력 부족 | 정상 0과 별도 상태. 원인과 관련 항목을 표시 |
| 저장 성공 후 화면 계산 실패 | 저장 성공 사실과 표시 실패 구분, 같은 저장 재실행 대신 자료 재조회 |
| 손상/미지원 백업 | 교체 전 중단, 기존 자료 유지 |
| 복원/일괄 등록 중 실패 | 한 DB 거래 전체 취소. 부분 정상 완료 표시 금지 |
| 프로그램 로딩/빌드 배포 실패 | Vercel/GitHub 빌드 결과 확인, 정상 배포 유지. 브라우저 저장 자료와 별개임을 안내 |
| DB 자체가 손상/호환 불가 | 자동 초기화 금지. 지원 버전/검증된 백업 복원으로 대응 |

앱 오류 로그에는 오류 코드·작업 종류·앱/구조 버전 정도만 남기고 실제 매출·메모·파일 원문은 남기지 않는다. 외부 오류 수집 서비스는 1차에 붙이지 않는다. Vercel 로그는 주로 배포/웹 제공 장애를 확인하며 브라우저 계산 오류를 모두 관찰할 수 없다는 한계를 둔다.

## 15. 검사와 출시 조건

- FRD T-01~T-17을 기능 검사 목록으로 유지한다. 미승인 기대값은 승인 후 채운다.
- 계산 모듈: 과거 원가 보존, 채널별 레시피, 기간 경계, 비용 이중 반영 방지, 실사 이중 적용 방지, 분모 0, 승인된 전망/발주/반올림 경계를 검사한다.
- 저장 모듈: 초기화 한 번, 추가/수정/삭제, 중복 클릭, 여러 탭 revision 충돌, 일괄 쓰기 실패, 복원 실패의 전부 취소, 재접속 보존, 구조 버전 변환을 검사한다.
- 파일 모듈: 내려받은 양식을 실제 다시 읽고, 날짜 체계·빈칸/0·UNKNOWN ID·파일 내 중복·수식/숨은 행 정책·손상/큰 파일을 검사한다.
- 백업: 전체 기록 수·ID 연결·당시 금액·실측량·설정·출처의 내보내기/복원 일치 확인. 계산 캐시 없이 결과를 다시 만들 수 있는지 검사한다.
- 브라우저: 최신 안정 Chrome/Edge의 정상 프로필에서 핵심 흐름과 다운로드 확인. 다른 브라우저/기기의 자동 공유는 기대하지 않는다.
- 배포: 운영/미리보기 분리, 새로고침, 프로덕션 자산 로딩, 원격 시안 자산 제거, 실제 자료가 빌드에 없는지, 앱 통신에 업무 자료 전송이 없는지 확인한다.
- 성능: 11절 목표를 제공 샘플과 시험 파일로 측정한다. 목표 초과 시 계산식 대신 조회/캐시/Worker 구조를 개선한다.

출시 완료 조건은 필수 기능 전부 작동, 핵심 FRD 정책 확정, 자동 검사/대표 브라우저 검사 통과, 재접속/복원 확인, 운영 주소와 요금제 적합성 확인이다. 정책 미정 상태에서 일부 화면만 보이는 배포는 시제품 미리보기로 구분한다.

## 16. 4시간 구현 계획과 남은 결정

PRD 시간 예산은 요구사항 30분·화면 30분·개발 120분·검사 30분·배포 30분이다. 개발 120분은 다음 순서로 배분한다.

| 시간 예산 | 구현 묶음 |
|---|---|
| 20분 | 앱 구조·공통 부품·DB·샘플 로딩 |
| 30분 | 승인된 계산 모듈·기간 집계·원본 연결 |
| 30분 | 판매/비용/재고 입력과 결과 화면 연결 |
| 25분 | 판매 엑셀 양식/검사/가져오기 |
| 15분 | 전체 백업/복원·실패 상태 |

시간표는 계획값이며 미측정 구현 완료 보장이 아니다. 필수 정책을 결정하는 시간을 포함해 4시간 목표를 점검한다. 지연 시 임의로 필수 기능을 빼거나 계산 기준을 단순화하지 않고 실제 진행과 범위/시간 조정을 사용자에게 알린다.

현재 남은 제품 결정은 FRD D-01~D-11 그대로다. 특히 신규 판매 금액/수수료·영업일과 마감 갱신·실사 순서·오류/중복 등록·전망 비용 처리는 완전한 구현 전에 필요하다. 기술 선택은 이 TRD대로 진행할 수 있지만 계산 정책 승인까지 대신하지 않는다.

운영 전 확인할 기술 전제는 '같은 기기·브라우저·운영 주소의 로컬 저장', '앱 로그인 없는 개인 기기 사용', '실운영 Vercel 요금제'다. 이를 여러 기기 자동 동기화·공용 단말 보호·무료 상업 배포로 오해하지 않게 한다.
